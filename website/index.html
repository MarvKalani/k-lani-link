Encrypted, local, peer-to-peer AI plumbing k-lani-link

A client application — such as OpenCode — talks to a local, OpenAI-compatible inference API. k-lani-link pairs two peers and authenticates them to each other, and the inference payloads ride a direct encrypted peer channel: WebRTC secured with DTLS plus an additional layer of content encryption. Direct does not mean LAN-only — that channel can traverse the public internet; the protection is cryptographic, not geographic.

Architecture

How the encrypted path works

Local API endpoint OPENAI-COMPATIBLE

The client app sends chat/completion calls to a local, OpenAI-compatible API. The inference backend behind that endpoint is replaceable: swap models or servers without changing the client.

The client never needs a public endpoint for the demo to work.

Peer pairing & authentication WEBRTC + DTLS

k-lani-link pairs the two peers and authenticates each to the other before any payload traffic flows. The two peers are the k-lani-link client on the app side and the k-lani-link host — the peer process running on the model machine, not a central hosting service. Transport is WebRTC: the channel is secured with DTLS, and payloads additionally pass through content-level encryption, so data is protected in transit and at the payload level.

Signaling closes after pairing DISCONNECT

Pairing is a setup step that completes before the first API call (not re-negotiated per request), and the signaling connection closes once pairing completes. A closed signaling socket right after rendezvous is the expected, healthy state — not an error and not an open attack surface.

Keep the two kinds of traffic apart: setup traffic (pairing, toward configured signaling/STUN services) versus inference payload traffic over the encrypted peer channel.

TURN is explicit opt-in OFF BY DEFAULT

TURN relay is disabled by default; enabling it requires an explicit setting, so no relay is involved unless you deliberately opt in. And a relay is not a man in the middle of your data: even when enabled, a TURN server only relays this peer connection — it carries the encrypted channel, not the plaintext inference payload.

Streaming responses STREAMED

Where the model/provider and the client both support it, responses — including reasoning fields and tool calls — arrive as a stream rather than one large blob, so the UI updates as tokens (and tool events) land.

Request path

One request, step by step

Client app (e.g. OpenCode) → k-lani-link client (client-side peer) → Encrypted peer channel → k-lani-link host (model machine) → Inference backend → Streamed reply, reasoning & tool calls
  1. Before any API call, two peer processes pair: the k-lani-link client on the app side and the k-lani-link host on the model machine rendezvous via a separate signaling broker — the host is one of the peers, not a central intermediary. They authenticate during pairing, and the signaling connection closes after pairing.
  2. The client app then talks to its local OpenAI-compatible API; each call's inference payload rides the already-established encrypted peer channel — DTLS on the transport, content encryption on the payload. Pairing is not re-requested per call.
  3. The channel is direct peer-to-peer and can still traverse the internet; direct does not mean LAN-only.
  4. Setup traffic (pairing toward configured signaling/STUN services) is distinct from payload traffic over the encrypted peer channel; if TURN is enabled explicitly, the relay carries only the encrypted channel.
  5. The inference backend answers with streamed model responses when supported; the backend behind the endpoint is swappable.

The privacy posture covers the channel: encrypted in transit, peer to peer — wherever that channel runs. It says nothing about what each peer's device stores, and it is not the same thing as keeping everything on a LAN.

Use case

The invoice-and-ledger workflow

What the demo does FICTIONAL

A small business workflow: an agent drafts a clearly laid-out one-page invoice for a fictional issuer and customer, then records the same line items in a spreadsheet ledger with quantity, rate and totals formulas. It shows an AI client doing practical office work end-to-end on the local encrypted path.

"Fictional" applies to the demo data: every person, document and figure is synthetic — no real customer data, identifiers or payment instructions exist anywhere in the demo. The architecture described on this page is the product's real one, not part of the fiction.

Accuracy

What this demo does not claim

  • No automatic GDPR compliance or certification. An encrypted channel does not certify GDPR conformance; compliance is a legal and organizational process, not a property a tool can grant you.
  • Organizational policy, device security and local history still matter. The agent keeps its own local history on the device, and transport encryption does nothing about endpoint security or company policy.
  • This recorded lab runs both peers on one machine. It demonstrates the encrypted path end to end; it is not a remote office-to-home benchmark.
  • No invented benchmarks. No speeds, latencies or throughput figures are published here, and no claim is made that the full 256K context window was used.
  • Support is not universal. This page does not claim that every browser, extension or client already supports this path.
  • The use-case data is fictional, the architecture is not. The customer, documents and figures are synthetic — that disclaimer covers the demo content only; the page describes the product's real architecture.
